# 0020: Reminders and proactive turns

Date: 2026-11-14
Status: Accepted

## Context

Reminders and timers are stored in the `reminders` table (migration 6) by the reminder tools, and several Lucy processes may share the database (`lucy chat`, `lucy voice`, `lucy listen`). When one comes due, Lucy has to speak first: a turn with no user message. ADR 0003 reserved `TimerFired` for this; until now it was ignored. Speaking at the wrong moment has two costs: talking over the user or over another reply, and landing between a confirmation question (ADR 0006) and its answer, so that a "yes" meant for the reminder could run a dangerous call.

## Decision

- **A turn without a user message, authored by code.** The orchestrator subscribes to `TimerFired` and queues it in the same per-session queue as user messages, so it waits behind a running turn and is never interleaved with one. Its handler is chosen by `TimerFired.name` from `timer_handlers` (`"reminder"` today; a daily brief can be added later) and returns the text to say, or nothing. The turn logs the `TimerFired` with its turn id, says the text exactly as a code-authored reply is said (`TextDelta`, `SentenceReady`, `AssistantMessage`), and ends with `TurnEnded`. There is no model call. An unknown name is logged and the turn ends silently.
- **Claim, lease, deliver.** The scheduler never speaks. `ReminderService` (`lucy.core.reminders`) offers `wait_due()`, which checks the store at least every 5 s (so reminders set by another process are noticed), and `fire(session_id)`, which atomically claims every due reminder for this process (`claim_due`) and returns one `TimerFired` naming their ids and the owner. The proactive turn renews the claim just before speaking (`begin_delivery`); rows cancelled meanwhile, or taken over by another process after the 60 s lease lapsed, are not said, and if none remain the turn says nothing. Several due at once are one message.
- **Repeat over loss.** Reminders are marked delivered after the words are logged. A crash between the claim and the logged reply leaves the row claimed; when the lease expires another `fire` takes it and it is said with the late wording ("A reminder was due at 16:00 today: ..."). A crash between the logged reply and the mark can say it twice. This is deliberately the opposite of the confirmation flow, which logs its decision first so a dangerous call can be lost but never repeated: a lost reminder is worse than a repeated one.
- **Client-gated delivery.** Only a client knows when the user is idle, so the client decides when to call `fire` and publishes the event on the bus, as it publishes a `UserMessage`. `lucy chat` runs a background task that waits for something due, waits a grace of 3 s (so a voice client on the same database claims first and the reminder is spoken rather than printed), takes the chat's floor lock (held by every user turn too), fires, publishes and prints `lucy> Reminder: ...` above the prompt, keeping a half-typed line. Started after the banner, it also delivers reminders that came due while Lucy was off.
- **The confirmation rule.** `fire` returns nothing while the session has a confirmation request that is unresolved, unanswered and unexpired (`confirm.open_request`, read from the episode log, so it holds across processes); the reminder comes after the answer or the expiry. For the race where a reminder was claimed before the question was asked: any `TimerFired` logged after a request makes it no longer pending, so a "yes" after a reminder can never run the older call. A proactive turn that finds such a request logs `ConfirmationResolved(outcome="superseded")` and adds "The change I asked about was not made; ask again if you still want it." A request made after a reminder confirms normally.
- **History and memory.** A proactive reply follows the previous reply with no user message between. `events_to_messages` merges a text-only assistant message into a preceding text-only assistant message (blank line between), so roles alternate as chat templates expect. Extraction skips a turn with no `UserMessage` without a model call, so reminders never become facts. Model residency counts a `TimerFired` as the start of a turn.

## Voice and wake listener

- **`VoiceSession.announce(fire, cue=None)`.** It takes the session's floor lock, which every utterance holds from its endpoint until its reply has been played, and waits until the session is idle: listening, the user not mid-utterance (`hearing_speech`), nothing being transcribed. Only then does it call `fire`, so the claim is made at the moment of delivery; None (nothing claimed, or a confirmation question open) returns without touching the session. The `TimerFired` goes through the same path as a `UserMessage` (`_converse` takes either): its turn is registered as expected before publishing, so the session's routing of unknown turn ids to the oldest unassigned turn can never give a reminder's events to a user turn, or the other way round. Its `SentenceReady` events are spoken by the same player; microphone frames are dropped while announcing, and the session then listens again with the usual tail gate. Proactive turns are not written to the voice timings file.
- **No grace.** The voice clients claim as soon as they are idle (`deliver_reminders`), so a reminder due while `lucy chat` also runs is spoken rather than printed.
- **Barge-in** works as for any reply: playback stops, the session listens again and `PlaybackInterrupted` records what was heard, so the history holds only the spoken part. The reminder still counts as delivered: the core marks it once its words are logged, which happens before playback starts.
- **`lucy voice`** starts the delivery task once the session is built (reminders that came due while Lucy was off are spoken, late, right after start) and cancels it on exit.
- **`lucy listen`.** The session's delivery task runs whatever the listener's state. While the session thinks or speaks, the wake stage is not fed and is reset, so Lucy never wakes on her own voice. Before the reminder the wake chime plays (when `[wake] chime` is on) so the user is not startled. When the session listens again after a reminder that came while waiting, the follow-up window opens as after a reply (awake for `followup_seconds`, buffered audio forgotten, no wake chime), so "thanks" or "remind me again in ten minutes" needs no wake phrase; the sleep chime closes it. Before the first wake there is no app: `run_listen` runs a store-only `ReminderService` (its `wait_due` only) and, when something is due, calls `WakeListener.rouse()`, which builds the session without a wake phrase while the listener stays waiting; the session's own delivery task then claims and speaks the reminder. That first reminder pays the model-loading delay (about 1.6 s).
- A reminder turn makes no model call, so announcing never loads the chat model; residency counts it busy only from its `TimerFired` to its `TurnEnded`.

## Consequences

- A reminder is said only while some client of the database is running and idle; one that came due while Lucy was off is said, late, at the next start.
- Two processes never both say a reminder within the lease; after a crash one may be said twice.
- A reminder never interrupts a running turn, and is held while a confirmation question is open, so it can be up to `confirm_timeout` late.
- The `TimerFired` handler interface can carry other proactive turns (a daily brief) without changing the orchestrator.
